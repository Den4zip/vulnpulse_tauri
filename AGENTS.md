# VulnPulse — правила разработки новой версии

Этот каталог — самостоятельный проект на **Tauri 2 + Rust + React/TypeScript**. Решение о новом стеке принято пользователем 2026-11-17. Локальные правила заменяют относящиеся к Electron, Main/preload, node:sqlite и Drizzle указания родительского проекта. Старый код служит справочным материалом; новые функции реализуются в архитектуре ниже.

## Начало работы и завершение этапа

1. В начале работы и перед ответом о состоянии проекта читать [PROJECT_MEMORY.md](PROJECT_MEMORY.md). Для выбора следующей задачи читать [PLAN.md](PLAN.md). Проверять фактические файлы и Git: план не является свидетельством реализации.
2. После значимых изменений обновлять память: дата, решение и его источник, готовые функции, проверки, ограничения и следующий шаг. Заменять устаревшие сведения. Секреты и пользовательские данные в память не записывать. Если подключён граф знаний именно этого проекта, синхронизировать его; иначе использовать локальную память.
3. Рабочая ветка — постоянная `develop`; готовый этап — один осмысленный коммит или набор связанных коммитов и PR в `main`. Коммит/PR создавать по завершении этапа, а не каждой функции. Слияние выполнять в пределах разрешения пользователя.
4. Этап закрывать после реализации, проверок, отчёта о результате и оставшихся ограничениях. Продолжать уже разрешённый объём без повторного согласования. Изменение утверждённых продуктовых правил, границ конфиденциальности или стека обсуждать с пользователем; обычные детали реализации выбирать самостоятельно.
5. Версии и рабочие команды брать из `package.json`, `package-lock.json`, `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`. До их появления команды в плане являются будущим контрактом. Для API библиотек использовать Context7 с учётом версии, затем официальные документы и установленные типы.

## Границы архитектуры

```text
React UI → типизированный клиент → Tauri commands → application services → domain
                                                     ↓
                                      repositories / HTTP / Vault / jobs
```

- **Rust владеет** сетью, файловыми операциями, SQLite, криптографией, планировщиком, матчингом и расчётами. TypeScript владеет представлением и состоянием интерфейса. Zustand хранит фильтры, выделение и UI-черновики; серверные сущности и бизнес-правила не дублировать в store.
- **Domain** — чистая логика без Tauri, React, HTTP и SQL. **Application** координирует операции и транзакции. **Infrastructure** реализует хранилища и внешние источники. Commands валидируют запрос, контекст окна/проекта и делегируют сервису.
- DTO определять независимо от таблиц БД; генерировать TypeScript из Rust-контрактов и проверять отсутствие расхождений в CI. Генерируемые файлы не редактировать вручную. На Rust-границе выполнять runtime-валидацию даже для типизированного клиента.
- Синхронные SQLite, KDF и разбор больших файлов выполнять вне потока интерфейса и async executor. Использовать ограниченную очередь/исполнителей; не создавать задачу на каждую запись. Отмена кооперативная: блокирующая задача должна проверять её между порциями.
- Длительная операция имеет `jobId`, этап, счётчики, отмену и итог. События адресовать нужному окну/сессии. UI отбрасывает ответы и события от старого проекта; после переподключения запрашивает актуальное состояние задания.
- Начать модульным приложением в одном Rust crate. Дополнительные crates, универсальные репозитории, плагины и распределённые сервисы вводить при доказанной необходимости.

## Данные, проекты и история

- Общий каталог содержит публичные записи источников и их происхождение. Чувствительные активы, установки, топология, findings, заметки, SLA и бизнес-данные принадлежат проекту и его Vault.
- SQL и миграции выполняются только Rust-репозиториями. Версионированные SQL-миграции входят в бандл, применяются транзакционно, имеют контрольные суммы. Применённые миграции неизменяемы. Проверять новую и заполненную базу, прерывание и восстановление.
- Между каталогом и отдельным проектным хранилищем использовать устойчивые ссылки источников и снимки доказательств, а не межбазовые внешние ключи. Анализ читает согласованную ревизию каталога.
- **Подтверждено пользователем:** обновление версии сохраняет ID установки; перенос на другой актив создаёт новую установку. Пересчёт не меняет ручной статус. Старые глобальные заметки и SLA остаются на исходных карточках; назначение finding — отдельное явное действие с происхождением.
- Целевая единица workflow — finding конкретной установки в проекте. Статусы: `New`, `Analyzing`, `Affected`, `In Progress`, `Patched`, `False Positive`. Применимость хранить отдельно: `affected`, `not_affected`, `unknown`. Отсутствие записи, ошибка и отмена не являются исправлением.
- Снимки завершённого анализа неизменяемы. Хранить ревизии входов, версию движка, полноту и доказательства. Сохранять последний полный снимок при неудаче следующего запуска; устаревание показывать явно.
- Импорт идемпотентен, имеет предварительный просмотр и разрешение конфликтов. Историю сохранять при архивировании. Политику окончательного удаления и объединения идентификаторов определить до соответствующей реализации.

## Сеть и источники

- Все запросы приложения проходят через единый Rust HTTP-сервис с общей политикой сети, TLS-проверкой, тайм-аутами, лимитами ответа, backoff и отменой. Фронтенд не вызывает внешние API и не получает HTTP/SQL/shell-плагины общего назначения.
- Новый профиль стартует с выключенными автообновлениями. Режим «Без сети» блокирует HTTP-сервис, расписания и проверку обновлений приложения. Сетевые шрифты, аналитика и внешние изображения отсутствуют. Обновления ОС/WebView находятся за границей этого переключателя; не обещать их блокировку.
- NVD: общий лимитер запросов; исходный бюджет 5 без ключа / 50 с ключом за 30 секунд, перед реализацией сверить условия поставщика. Учитывать 429 и `Retry-After`. Ключ доступен только Rust, ввод — отдельная write-only операция, ответ — наличие ключа.
- OSV: локальный JSON без передачи инвентаря. `querybatch`, отправку стека и облачный анализ не включать без отдельного решения пользователя.
- ФСТЭК: основной путь — локальный XML/XML.GZ; зеркало — явно обозначенный неофициальный источник. Потоковый парсер, запрет DTD/внешних сущностей, лимиты распаковки, глубины и размера записи. TLS-проверку не отключать.
- Отдельно показывать публикацию, изменение записи, получение данных и последний полностью успешный импорт. Сохранять конфликты источников; KEV и CVSS имеют происхождение. Совпадение названий не доказывает идентичность продукта или CVE.

## Применимость и риск

- Matcher работает с CPE 2.3, PURL и явной семантикой версий экосистемы. Переносить проверенные сценарии старого matcher в общий корпус тестовых данных. Не считать Rust semver полной заменой npm ranges, PyPI, Maven или системных версий.
- `unknown` — полноценный результат с причиной. Неподдержанная логика NVD/OSV не превращается в `not_affected`. Версии сравнивать специализированными правилами; преобразование версии целиком в число запрещено.
- Для чистого matcher требовать 100% измеримого покрытия строк/функций и всех достижимых ветвей правил; дополнительно таблицы границ, property-тесты и независимые ожидаемые результаты. Указывать ограничения Rust-инструмента покрытия, не выдавать покрытие строк за покрытие ветвей.
- Связность графа, применимость CVE, сценарий атаки, приоритет и денежные последствия — разные сущности. CVSS не является вероятностью; confidence matcher тоже. What-If сравнивает одинаковые версии каталога/правил и раскрывает изменённые предпосылки. Денежные значения вычислять десятичной арифметикой или целыми минимальными единицами.

## Безопасность Tauri и Vault

- Явно ограничить capabilities, permissions, окна и custom commands. Одной регистрации `invoke_handler` недостаточно для ограничения собственных команд; включить их в механизм разрешений и проверить отрицательные сценарии. Подробности и источник — [PLAN.md](PLAN.md).
- Загружать только локальный UI. CSP, запрет произвольной навигации, проверка схем внешних ссылок и минимальные scopes обязательны. Данные фидов, имена узлов и заметки отображать как недоверенный текст. Для путей из UI проверять доступ и нормализацию на Rust-границе.
- Пароли и ключи не возвращать в response DTO, ошибки, события, логи и телеметрию. Краткоживущий ввод пароля очищать в UI после отправки; расшифрованный проект не сохранять в localStorage/IndexedDB. Заблокированный Vault очищает чувствительное UI-состояние и отвергает операции старой сессии.
- До выбора и проверки Vault использовать только синтетические проекты в памяти. Защита файла, временных данных, журналов, экспортов и резервных копий должна быть явно определена. Молчаливого plaintext fallback нет.
- Криптографические примитивы брать из поддерживаемых библиотек; формат контейнера, параметры KDF и жизненный цикл ключей фиксировать отдельным решением и проверять тестовыми векторами, повреждениями и сбоями сохранения. До независимого ревью не объявлять Vault защищённым для production.
- Тесты используют отдельные временные профили и фикстуры. Рабочую базу пользователя не открывать и не изменять для проверки. Тестовые WebDriver-плагины, debug-команды и обходы авторизации исключить из release.

## Интерфейс и визуальная приёмка

- До изменения UI читать визуальную спецификацию в [PLAN.md](PLAN.md) и [референсы](references/README.md). Основа — Mint из Figma: светлый серо-сиреневый фон, белые панели, фиолетовый акцент, плотные таблицы. Сохранять атрибуцию автора и лицензии.
- React/TypeScript, Tailwind, shadcn/ui, lucide-react, Recharts и Zustand сохраняются. Топология — React Flow как кандидат для проверки. WebView не получает бизнес-логику расчётов графа.
- Каждый экран имеет загрузку, пустую базу, пустой фильтр, ошибку/повтор, недоступное действие; формы — конфликт и сохранение черновика при ошибке. Долгие операции — честный прогресс и отмену. Не показывать успех до фиксации данных.
- Проверять клавиатуру, доступные имена, восстановление фокуса и текстовые обозначения статусов. Основная проверка — 1280×800 при 100/125/150%; 1024×768 — дополнительная. Сравнивать реальные скриншоты с локальными референсами; не заявлять точное совпадение с неизвлечёнными слоями Figma.

## Проверки и передача результата

- Для кода: TypeScript typecheck, lint, frontend tests/coverage, Rust fmt/clippy/tests/coverage, сборка UI и Tauri. Для затронутого сценария — desktop E2E; перед завершением этапа — весь доступный обязательный CI-набор. Границы coverage указывать отдельно для UI, domain, services и интеграций.
- Браузерный тест с mock IPC не заменяет тест установленного Tauri-приложения. Проверять runtime/WebView и криптографию в поставляемой сборке. Зависимости и драйверы подготавливать один раз до параллельных тестов; тесты не скачивают общий runtime самостоятельно.
- Для документации: проверить локальные ссылки, согласованность статусов/источников и отсутствие обещаний непроверенных функций. Невыполненные проверки перечислить в отчёте. Не запускать весь набор приложения ради правки текста.
- Старый проект и его архив сохранять до выполнения критериев переноса из плана. Источник кода и история сохранены в `references/legacy-history.bundle`; это не резервная копия пользовательских баз, секретов или игнорируемых файлов.
